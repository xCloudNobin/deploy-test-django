# Django Taskboard

A meaningful Django application for the xCloud app-compatibility suite:
a project/task board with **ORM migrations**, **login/session auth**,
**validated CRUD**, a **real background job** with a documented worker
command, persistent storage, and separate liveness/readiness endpoints.

It is a production-process fixture, not a success-page shell: every workflow
reads and writes through Django's ORM, all mutations are protected by CSRF
and authentication, and `scripts/verify.sh` exercises the real gunicorn
process end to end.

## Feature summary

- Projects and tasks with status, priority, due date, search and filters.
- Classic Django auth: login/logout, session cookies, `login_required` views.
- Server-side validation via Django forms with meaningful error messages.
- ORM model migrations (`python manage.py migrate`) and idempotent seed data
  (`python manage.py seed`).
- One background job: `recompute_project_progress`. Task writes enqueue a
  `Job` row; the documented worker command drains jobs and recomputes each
  project's progress percentage.
- Persistence: explicit SQLite file path (`DATABASE_NAME` / `DATA_DIR`);
  `scripts/smoke.sh` restarts the production process and proves data survives.
- `/health/live` (process alive) and `/health/ready` (queries the database;
  503 when the database is unavailable). Page routes degrade to 503 when the
  database goes down instead of leaking stack traces.
- Non-sensitive release marker rendered in the UI footer, generated by
  `scripts/build.sh` into `VERSION` (git SHA by default).

## Quick start (development)

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
cp .env.example .env          # review and adjust
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed                          # optional demo data
.venv/bin/python manage.py ensureuser --username demo --password change-me
.venv/bin/python manage.py runserver 0.0.0.0:8000
```

Open http://localhost:8000, log in with the account created above, and use
the project/task board.

## Production start

```bash
.venv/bin/python manage.py migrate
.venv/bin/python manage.py ensureuser --username app --password "$APP_PASSWORD"
.venv/bin/python manage.py collectstatic --noinput   # optional (admin assets)
gunicorn -c gunicorn.conf.py config.wsgi:application
```

- Binds to `BIND_HOST:PORT` (defaults **0.0.0.0:8000**), configurable via env.
- `WEB_CONCURRENCY` controls gunicorn workers (default 2).
- Logs go to stdout/stderr (`GUNICORN_ACCESSLOG`, `GUNICORN_ERRORLOG`).

### Background worker

Task writes enqueue a `Job` row. Run the worker alongside the web server to
drain them:

```bash
# long-running worker (polls every second)
.venv/bin/python manage.py runworker

# drain currently queued jobs and exit (used by tests/smoke)
.venv/bin/python manage.py runworker --once
```

A job is claimed (`queued -> running`), its registered handler
(`jobs/handlers.py`) is executed, and the outcome is recorded
(`succeeded`/`failed` with result/error). The built-in job recomputes each
project's progress = done tasks / total tasks.

## Health and readiness

| Endpoint        | Meaning                                                            |
|-----------------|--------------------------------------------------------------------|
| `GET /health/live`  | Process is alive (always 200 while the worker accepts requests). |
| `GET /health/ready` | Database reachable → 200; otherwise **503**.                     |

Mutating and list routes return **503** when the database is unavailable
via the `ServiceUnavailableMiddleware` (no stack traces exposed).

## Environment variables

See `.env.example` for the full commented list.

| Variable | Required | Default | Purpose |
|----------|----------|---------|---------|
| `DJANGO_SECRET_KEY` | yes (prod) | insecure dev value | session/hash signing |
| `DJANGO_DEBUG` | no | `0` | Django debug mode |
| `DJANGO_ALLOWED_HOSTS` | yes (prod) | `127.0.0.1,localhost` | allowed hosts |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | no | localhost origins | host-aware CSRF behind proxies |
| `PORT` | no | `8000` | gunicorn bind port |
| `BIND_HOST` | no | `0.0.0.0` | gunicorn bind host |
| `WEB_CONCURRENCY` | no | `2` | gunicorn worker count |
| `TZ` | no | `UTC` | timezone |
| `DATA_DIR` | no | `<repo>/data` | base data directory |
| `DATABASE_NAME` | no | `<DATA_DIR>/db.sqlite3` | **persistent SQLite path** |
| `BUILD_MARKER` | no | git SHA | release marker in UI footer |

No credentials or secrets are committed. Platforms must inject the real
`DJANGO_SECRET_KEY` and account password at deploy time.

## Persistence

Data lives in the SQLite file at `DATABASE_NAME`. For redeploys that reuse or
replace the release directory, deploy with a persistent volume (or dedicated
database) mounted at `DATA_DIR`/`DATABASE_NAME` so the file survives. The app
never writes permanent state into an ephemeral release directory.

`scripts/smoke.sh` proves persistence: it creates a "survivor" project over
HTTP, gracefully stops gunicorn, restarts on the **same database path**, and
verifies the record is still served.

## Schema

Migrated via Django migrations (`taskboard/migrations/0001_initial.py`,
`jobs/migrations/0001_initial.py`):

- `taskboard_project`: name, description, status, progress, timestamps.
- `taskboard_task`: project FK, title, description, status, priority, due_date, timestamps.
- `jobs_job`: name, args (JSON), status, result (JSON), error, timestamps.

`python manage.py makemigrations --check --dry-run` must report no pending
changes; `scripts/verify.sh` asserts this.

## Automated verification

```bash
scripts/verify.sh
```

Runs, in order:

1. `scripts/build.sh` — writes `VERSION` release marker.
2. Fresh virtualenv + clean `pip install -r requirements-dev.txt`.
3. `manage.py check` and `manage.py makemigrations --check --dry-run`.
4. pytest suite (auth/session, CRUD validation, escaping, health/readiness,
   background worker, migration/seed idempotency).
5. `scripts/smoke.sh` — real gunicorn process: login/session, HTML CRUD,
   search/filter, CSRF-negative and validation-negative cases, worker run,
   graceful stop + restart persistence, database-unavailable readiness.

Exit 0 only when every check passes. Recorded outcomes: see `VERIFICATION.md`
and the PR description.
